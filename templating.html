Page Templates & Shared Building Blocks

The Journal's Page Templates

How Adventure Journal draws its pages: from one giant file hard-coded for dungeons, to shared building blocks and short templates that turn the DataStore's records into dungeon pages, raid pages and quest pages.

Engineered with Opus 5.5

Architected with Claude Opus 5.5

The v0.11 template system was designed and built through agentic workflows using Anthropic's Claude Opus 5.5 model. Opus 5.5 audited the old Dungeons files line by line, split them into shared building blocks without changing a single thing players see, built the template engine and the quest template on top of them, wrote the guide for adding new content, and then used that guide to build the Raids tab from data alone.

Same Pages, New Foundation ? What changed in v0.11? Almost nothing you can see, on purpose. The dungeon pages look the way they did in v0.10. What changed is how they're built underneath, which is what made the Raids tab possible.

In v0.9, we moved all of the Journal's data into one shared DataStore, but the pages that displayed that data were still custom-built just for dungeons. Version 0.11 replaces those one-off pages with a template system made of reusable building blocks. Instead of building a brand-new page from scratch for every tab, we now use a short template that tells those building blocks what data to show and how to arrange it.

Before & After

Before • v0.10 and Earlier

One Giant File That Did Everything

Every dungeon page was drawn by a single 4,019-line file: the boss list, the loot, the side tabs, the wing page, the quest list, and the quest details were all packed together, switching between views with a tangle of if this, then that.

  • The page's shape was written in code. Which sections the boss list has, their order, the tabs, and every label were hard-coded into the file. The word "Dungeon" appeared 134 times.
  • The same pieces were built over and over. The boss button, the level tag, the faction crest and the quest details were each written two to five times.
  • Special cases lived in code. Which capital-city dungeons show a faction crest, which bosses appear under a specific dungeon wing, how card artwork is cropped, and which quest givers get a map pin were all hard-coded into the file, etc.
  • Raids had to copy it. The first Raids attempt was a 1,200-line copy of the Dungeons page code that broke whenever the Dungeons tab was turned off.
After • v0.11+

Templates on Shared Blocks

The giant file is gone. Its pieces became 25 shared building blocks, and each kind of page is described by a short template that says what the page shows and in what order.

  • The page's shape is data. Boss list sections, tabs, loot categories, and every label on the page come from the template—so the same shared page layout automatically says "Raid Overview" instead of "Dungeon Overview" without needing a separate copy of the page code.
  • Every piece is built once. One boss button, one level tag, one crest, one quest page, shared by Dungeons and Raids alike.
  • Special cases are data too. The crests, a boss shown on a specific wing, or where a card's picture is cropped are small entries next to the data, not code.
  • Raids are three short files. The Raids tab extends the dungeon page's template and changes only what's different: its name, its settings, and the group size in the header.

Three Layers, One Job Each ? Why layers? When each layer has one job, a change lands in one place. A new word goes in a template, a new look goes in a block, and a fix to the data shows up on every page that uses it.

What a Template Looks Like

The Raid Template

A Dungeon Page, With a Few Changes

This is the heart of the Raids tab (shortened). It starts from the shared instance page and lists only what's different about raids.

Templates:Extend("instance", "raid", { noun = "Raid", settings = "raids", -- "Lv 60 • 40 Players • Dustwallow Marsh" headerMeta = { "level", "size", "location" }, -- Raid cards show the group size, grouped by tier listInfo = "size", listGroups = { field = "tier" }, -- The boss list's sections, in order encounterSections = { { kind = "boss" }, { kind = "rare", label = "Rare Encounters" }, { kind = "minor", label = "Minor & Quest Encounters" }, }, })
Display Choices

One Page, Adjusted by Data ? Data or display? If the information is wrong, the information is fixed, and every page sees it. If it's right but should look different on one page, a display choice is added instead, and the information stays true.

When one page needs to look a little different, a small entry next to the data says so. Each one names exactly what it changes, so there's never a hidden special case in the code.

-- Onyxia's Lair: center the list card's picture -- higher, on the adventurers and the dragon's head { key = 249, kind = "replace", target = "card.crop", value = { centerV = 0.40 } } -- Stormwind's dungeon shows the Alliance crest { key = 34, kind = "replace", target = "header.crest", value = "Alliance" }

Six kinds cover it: replace, hide, note, banner, place (show a boss on a particular wing) and layout (draw a page with a different template).

How We Got There

Step 1 • No Visible Change

Split the Giant File

The 4,019-line file was taken apart into building blocks one piece at a time. Before and after, a tool recorded every text, picture and position on 13 pages, and showed no visible change.

Step 2 • The Engine

Templates for Dungeons & Quests

The template engine came next, then the dungeon template and a quest template used by every dungeon's Quests tab. The words, sections and special cases moved out of the code and into templates and data.

Step 3 • The Real Test

Raids From Data

Raids were built by following the new content guide: Onyxia's Lair with its attunement questlines, plus Hyjal Summit and The Barrow Deeps waiting with placeholder bosses until the game adds them.

Built for What's Next

Made Possible

New Tabs From Templates

  • A Quests tab can reuse the quest template every dungeon and raid already uses.
  • Professions is a list with details, the same shape as the dungeon book, so it starts from the shared blocks.
  • Special quest pages, like a legendary weapon's questline, can get a page of their own as a second quest template.
  • New raids appear as soon as their data arrives: no new code.
Lessons Learned

What This Taught Us

  • Move first, change later. Splitting the giant file with no visible change made every later step safe to check.
  • Words belong to the page, not the code. Once the labels moved into templates, Raids needed almost nothing new.
  • A failed attempt is useful. The first Raids copy showed exactly which pieces had to be shared.
  • A guide beats a script. Every new piece of content is a little different, so we wrote instructions and a catalog of parts instead of a fixed recipe.
