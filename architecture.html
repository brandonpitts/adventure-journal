Core Item Storage Engine

An under-the-hood look at how Adventure Journal normalizes item records, resolves multi-source drop graphs, and evaluates compound multi-tag and minimum-level queries in sub-millisecond time.

Data Pipeline & Runtime Topology

Tier 1 • Normalized Static Data Layer Core/Data/
Items_Catalog.lua

Master dictionary defining each unique itemID exactly once using an Elastic Progressive Record Schema (name, category, quality, slot, subtype, reqLevel, and canonical tags).

Drops_Dungeons.lua

Domain association table mapping 35 Classic and WoW Forever dungeons and encounter keys to lightweight numeric itemID arrays without duplicating item metadata.

Canonical encounter alias resolution (folding chests, coffers, and trash pools into unified keys), composite boss definitions, and explicit category overrides.

TagTaxonomy.lua

Canonical 8-dimension tag registry, 120+ natural-language search synonyms, synchronous DBC classifiers, and live tooltip line parsers.

Architectural Design Decisions

Normalization vs. Duplication

Master Item Store + Domain Source Tables

In World of Warcraft, a single item can be acquired from multiple distinct sources: shared dungeon boss pools, zone-wide trash drops, seasonal holiday bosses, or quest rewards. Storing item metadata inline inside individual dungeon or quest files either causes data drift or slows down global searches.

Adventure Journal solves this with a relational split: every item is defined once in Items_Catalog.lua, while domain source files store only compact arrays of numeric itemIDs. At load time, ItemDatabase:Init() links both directions in memory in under 2 milliseconds.

-- Core/Data/Items_Catalog.lua (Defined Once) [1482] = { name = "Shadowfang", cat = "LOOT", q = 3, reqLevel = 19, slot = "Main Hand", subType = "Sword", tags = { "agility", "boe", "chance-on-hit", "dungeon", "loot", "main-hand", "one-hand", "shadow-damage", "sword", "weapon", "zone-drop" }, verified = true }
Client Cache Constraints

Cold-Cache Resilience in WoW 16001

The WoW client splits item APIs into two tiers: C_Item.GetItemInfoInstant(itemID) reads local client DBC tables synchronously (returning class, subclass, equip location, and icon), whereas C_Item.GetItemInfo(itemID) and tooltip scanning require the item to exist in the player's local WDB cache.

If an addon relies solely on runtime client queries, searching for an item or stat on a fresh install fails for any uncached item. By pre-hydrating English item names, quality tiers, slots, and canonical tags in Items_Catalog.lua, multi-tag searches work immediately on a cold cache while asynchronous server requests hydrate live localized tooltips in the background.

-- Compound Query Parser Examples "one handed, sword, dungeon" --> tags: {"one-hand", "sword", "dungeon"} "cloth, intellect, lvl 30-40" --> tags: {"cloth", "intellect"}, min: 30, max: 40 "1h mace >=45" --> tags: {"one-hand", "mace"}, min: 45 "sp, crit, trinket" --> tags: {"spell-power", "crit", "trinket"}
