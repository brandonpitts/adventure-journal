System Architecture & Data Engineering

The Journal's Data Engine

An under-the-hood look at how Adventure Journal keeps track of the game: from loot lists typed into each screen, to one engine for items, to a complete DataStore behind every dungeon, boss, quest and map pin.

? Three Generations of the Journal Each tab shows how the Journal stored its information in that era. v0.9+ is today's DataStore, a rebuild of all of the Journal's data, not just items. The older tabs are kept so you can see how far it has come.
Engineered with Opus 5.5

Architected with Claude Opus 5.5

The v0.9 DataStore was designed and built through agentic workflows using Anthropic's Claude Opus 5.5 model. Opus 5.5 ran the full audit of the old data, checked every record against the game's own files, built the eleven stores and their rules, wrote the tools that move and verify the data, rebuilt the Dungeons tab and the world map on top of it, and retired about 15,000 lines of old code along the way.

Not Just Items: A Ground-Up Rebuild ? What changed in v0.9? v0.6 rebuilt how the Journal stores items. v0.9 goes much further: every kind of information the Journal shows (dungeons, bosses, creatures, quests, map pins, zones) now lives in one shared system, the DataStore.

Version 0.6 gave the Journal a proper home for items. Everything else (dungeons, bosses, quests and map pins) still lived in separate lists, typed into each screen by hand and connected to each other by name. Version 0.9 replaces all of it with one shared system, the DataStore, so every page of the Journal reads from the same place, and future features (raids, a quest journal, dungeon maps) can be added as new information instead of new copies of old screens.

Why We Rebuilt Everything

The Trigger

Raids Didn't Fit

The first attempt at a Raids tab copied about 1,200 lines of the Dungeons screens, and broke whenever the Dungeons tab was turned off. Adding new content meant copying screens, not adding information. That showed us the real problem was underneath the screens.

What We Found

A Full Audit ? The Audit Before designing anything, we compared every list in the Journal with the game's own data. Most of these mistakes were invisible until something checked them.

  • Stratholme's loot was swapped between its two halves, so most of its bosses showed nothing.
  • About 25 bosses were named differently from the game.
  • Some quests were titled with an NPC's name instead of the quest's.
  • 31 items didn't exist in WoW Forever at all.

The Big Idea: Ask the Game ? A reference library, not a copy Like a library catalog that tells you where a book is instead of photocopying it, the DataStore keeps track of which game records the Journal uses and asks the game for the details.

WoW Forever already ships with Blizzard's own tables: every dungeon, every boss fight in order, every loading screen and flight point. We had been typing in, by hand, facts the game could tell us. So the DataStore doesn't copy the game. For each record it keeps only three things:

1 • The Game's Own Number

An ID ? What's an ID? Every item, creature, quest and dungeon in WoW has a permanent number. Names can change or be spelled differently; the number never does, so the Journal connects everything by number.

How the Journal asks the game for a record's current name, icon, quality and stats, so they're always right, even after a game patch.

2 • A Readable Name, and 3 • Our Own Knowledge

Labels & Links

A plain name so people can read the files (and something to show while the game is loading), plus the things the game doesn't know: which bosses are in which dungeon, what they drop, who starts each quest, helpful hints, and search tags.

Groundwork for What's Next

Already in v0.9

You Can See It Today

  • Opens where you are: open the Journal inside a dungeon and it goes straight to that dungeon, or to the exact wing you're standing in.
  • Map and Journal agree: entrance pins, levels and flight points come from the same records.
  • Corrected data: the game's own boss names, quest titles and loading screens.
Made Possible

Built to Grow

  • Raids become new records, not copied screens.
  • A quest journal can read the 519 quests already stored.
  • Dungeon maps: the named rooms of each dungeon are already being recorded.
  • "Where do I get this?" every way to get an item is already linked.

Lessons Learned

  • Check before you design. The audit changed the plan more than any idea did.
  • The game is the source of truth. Every time we asked the game instead of trusting a list, we found something.
  • A failed attempt is useful. The first raid build showed exactly what was missing.
  • Prove a tool by running it twice. A refresh that changes nothing the second time can be trusted the first time.
  • Keep the part only you know. "Nalpak, above the entrance to Wailing Caverns, The Barrens" became just the hint "Above the entrance to Wailing Caverns": his name and zone already live on his record.
How It Was Built, Step by Step
  1. Audit: every list in the Journal, and every screen that reads it, inventoried and checked against the game.
  2. Design: each store defined field by field, with the rules every record must pass.
  3. Plan: the build broken into steps, with a list of every old file that had to go.
  4. Foundations: the empty DataStore built and tested while the Journal kept running on its old data.
  5. Moving tools: scripts that move the old data in, checking every value on the way.
  6. Filling the stores: one store at a time, every link between them checked.
  7. Dungeons tab: switched to the new data; about 5,500 lines of old code removed.
  8. World map: pins and zone levels moved to the same records.
  9. Old quest module retired: about 8,800 lines removed.
  10. Keeping it current: the refresh, plus a safe way to bring in data from other sources (the game confirms it first).
  11. Polish: new dungeon cards, side tabs, wing detection, background choices.
Engineered with Argon

Architected with Gemini 4 Argon

The v0.6 – v0.8 Central Item Storage Engine was designed and developed through agentic workflows utilizing Google's Argon model. Argon was leveraged for complex architectural reasoning: transforming legacy siloed dungeon loot tables into a normalized relational data model (Items_Catalog.lua), formulating the 8-dimension inverted tag taxonomy, and engineering the sub-millisecond O(1) query evaluation engine and true :OnUnload() memory reclamation pipeline.

Architectural Design Decisions

Normalization vs. Duplication

Item Store + Domain Source Tables ? Elastic Progressive Record Schema Each item in Items_Catalog.lua only stores the fields it needs (no bloated empty keys), and automatically enriches itself with live tooltip stats when seen in-game.

In World of Warcraft, a single item can be acquired from multiple distinct sources: shared dungeon boss pools, zone-wide trash drops, seasonal holiday bosses, or quest rewards. Storing item metadata inline inside individual dungeon or quest files either causes data drift or slows down global searches.

Adventure Journal solves this with a relational split: every item is defined once in Items_Catalog.lua, while domain source files store only compact arrays of numeric itemIDs. At load time, ItemDatabase links both directions in memory.

-- Core/Data/Items_Catalog.lua (Defined Once) [1482] = { name = "Shadowfang", cat = "LOOT", q = 3, reqLevel = 19, slot = "Main Hand", subType = "Sword", tags = { "agility", "boe", "chance-on-hit", "dungeon", "loot", "main-hand", "one-hand", "shadow-damage", "sword", "weapon", "zone-drop" }, verified = true }
Client Cache Constraints

Cold-Cache Resilience in WoW 16001 ? DBC vs. WDB Server Cache GetItemInfoInstant reads local game files (DBC) that are always available offline. GetItemInfo reads the server cache (WDB), which only populates after the server sends item details.

The WoW client splits item APIs into two tiers: C_Item.GetItemInfoInstant(itemID) reads local client DBC tables synchronously (returning class, subclass, equip location, and icon), whereas C_Item.GetItemInfo(itemID) and tooltip scanning require the item to exist in the player's local WDB cache.

By filtering on instant DBC tags first and immediately hydrating and scanning candidate item tooltips on demand, compound searches like "two handed sword strength" work seamlessly without requiring you to browse and mouse over items beforehand.

-- Compound Query Parser Examples "one handed, sword, dungeon" --> tags: {"one-hand", "sword", "dungeon"} "cloth, intellect, lvl 30-40" --> tags: {"cloth", "intellect"}, min: 30, max: 40 "1h mace >=45" --> tags: {"one-hand", "mace"}, min: 45 "sp, crit, trinket" --> tags: {"spell-power", "crit", "trinket"}

Why We Outgrew the Legacy Model

Bottleneck 01 • Cold-Cache Blind Spots

Uncached Items Couldn't Be Searched ? The "Mouseover First" Problem In WoW, if you haven't seen an item yet, the client doesn't have its tooltip cached. Relying purely on live client queries meant uncached items were invisible to stat searches.

In the legacy model, item names, subtypes, and stats were resolved purely at runtime from the game client's local WDB cache. On a fresh install—or after clearing the game cache—searching for an item name or stat only matched items the player had already encountered or manually moused over inside a dungeon book.

Moving to the v0.6 Central Engine solved this by pre-hydrating static item names, quality tiers, and tags in Items_Catalog.lua while pairing synchronous GetItemInfoInstant DBC classification with on-demand candidate tooltip scanning.

Bottleneck 02 • Cross-Module Silos

Preparing for Quests, Raids & Professions ? One Item, Many Sources An item might drop in a dungeon, be required for a quest chain, and be crafted by a profession. Centralizing items in Core/ lets every module share one truth.

Because the original item tables lived inside Modules/Journal_Dungeons/, upcoming modules like Quests, Raids, and Professions would have either depended on the Dungeons module being loaded or duplicated thousands of item definitions.

By lifting item storage into Core/ItemDatabase.lua and introducing true :OnUnload() memory reclamation, modules are now genuinely independent and only consume memory when enabled.
